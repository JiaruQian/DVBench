# dv-005-calculator: Build a Complete UVM Verification Environment

Read `public/spec.md`, `public/ports.md`, `public/submission_format.md`, `submission_contract.json` and `public/debug_feedback.md`. The DUT top is `exdbin_mac`. There are no overridable top parameters; preserve the fixed default configuration. This is a purely combinational interface with no clock, reset, handshake or inout ports. Preserve the ascending packed ranges: `alu_cmd[0:3]`, `fxu_areg_q[0:63]`, `fxu_breg_q[0:63]` and `bin_sum[0:63]`; `local_error_found` and `bin_ovfl` are scalars. All ports are unsigned, and index 0 is the most significant bit. The RTL implementation is hidden; build your verification from the public behavior and native interface contracts.

Submit `flow/features.md`, `flow/features.json`, `flow/testplan.md`, `flow/testplan.json`, self-contained `model/model.sv`, all HDL needed for a complete UVM environment, and `sources.f`. Features explain what behavior is verified; the testplan explains how legal stimulus reaches the stated conditions, how expected results are predicted, when outputs are sampled, and how failures are detected. Follow the field types and references in `public/submission_format.md`: the JSON roots contain nonempty `features` and `tests` arrays, respectively. Feature entries carry `feature_id`, `requirement_ids`, `module`, `definition`, `interface`, `timing` and `boundary`; plan entries carry `test_id`, `feature_ids`, `requirement_ids`, `stimulus`, `expected`, `checker`, `implementation_id` and `source`. Use unique IDs, public requirement references, native interface names and real implementation locations as specified by the format. Use the same IDs and references in each Markdown/JSON pair, and put the complete facts in JSON; Markdown cannot fill JSON omissions. The two representations must agree semantically. You choose reasonable feature and test groupings.

Use UVM 1.2 with top `dvbench_top` and test `dvbench_test`. Connect independent expected predictions to actual/expected scoreboard comparisons in the complete environment. End finite stimulus, drain intended in-flight transactions, and release objections. Report failures with `UVM_ERROR`/`UVM_FATAL`. Print `DVBench_COMPLETED` exactly once after checks, draining and objections finish, only when both error and fatal counts are zero. The completion marker does not replace meaningful checks.

Instantiate the native DUT directly once in `dvbench_top`; do not define a replacement or submit a DUT implementation or empty stub. Interact only through native ports. Hidden hierarchical access, `bind`, `force`/`release`, DPI/VPI, file/system probing, network workarounds, arbitrary dumps and parameter overrides are prohibited. Only standard UVM macros and ordinary empty header-guard defines are permitted; do not use macro token concatenation or escaped identifiers. `sources.f` contains one ordered submission-relative `.sv`/`.v` HDL path per line and includes `model/model.sv`; do not include options, comments, wildcards, absolute paths, parent traversal, scripts, generated file names or DUT copies. Includes other than the provided `uvm_macros.svh` must be inside the submission and resolve relative to its root. The evaluator supplies fixed RTL and compilation options.

## Mandatory Independent Model Entry Point

`model/model.sv` must define the self-contained SystemVerilog module `dvbench_model`. It must compile independently of UVM and all other submission sources. Match the six native port names, directions, widths and ascending index ranges listed above and in the public specification and `submission_contract.json`. Do not add clock, reset or parameter ports. Derive combinational expected outputs from the native input values, independently of DUT actual outputs. Do not instantiate the DUT in the model or use DUT actual outputs as predictions. Use this identical file both for independent model evaluation and for prediction in the testbench scoreboard, with DUT actual and model expected outputs wired separately. Classes, packages or functions alone do not satisfy the module entry point.

Keep feedback outside the submission directory. The service uses the golden design and seed 1; mutation results are available only after the submission is frozen.

You have at most **300 cumulative agent decision turns**, with a delivery reminder at turn **250**. The budget persists across compaction and recovery of the same run. There is no whole-task wall-time or cumulative token limit. Compilation, simulation, and individual model requests have separate limits; read `public/deployment_budget.json`.

Read failed feedback and its listed compiler logs, simulation logs, and public-interface waveforms. Repair the submission and rerun while budget remains. A golden PASS is a debugging milestone: complete every required document, the independent model, and the UVM environment, and address known failures before finishing. Save the complete submission and report its actual verification status. Do not use subagents.
