# dv-026-clint: Build a Complete UVM Verification Environment

Read `public/spec.md`, `public/ports.md`, `public/submission_format.md`, and `submission_contract.json`, together with `public/debug_feedback.md`. The native DUT top is `CLINT`. There are no top-level parameters. The RTL implementation is hidden.

Submit `flow/features.md`, `flow/features.json`, `flow/testplan.md`, `flow/testplan.json`, a self-contained `model/model.sv`, all complete UVM sources, and `sources.f` at the submission root. Features explain what to verify; the test plan explains legal preparation, stimulus, independent expectations, valid sampling, and failure detection. Each Markdown/JSON pair must use the same IDs and references and agree semantically. JSON must carry every fact in full; Markdown cannot supply omitted facts. Contradictory facts under the same conditions, history, and observation window are errors for the affected obligations. Follow `public/submission_format.md` for types, references, and the unrelated paired examples.

The JSON feature root contains a nonempty `features` array. Required text fields are nonempty strings; requirement and interface references are nonempty arrays of distinct strings. Each feature supplies `feature_id`, `requirement_ids`, `module`, `definition`, `interface`, `timing`, and `boundary`; IDs are unique, requirement references come from the public specification, and interfaces identify relevant native ports. Optional `parent_id` references an existing feature or is null and must not form a cycle. The plan root contains a nonempty `tests` array; each test supplies unique `test_id`, valid `feature_ids` and `requirement_ids`, and complete `stimulus`, `expected`, and `checker` descriptions. Plan text and implementation locators are nonempty strings, and feature/requirement references are nonempty arrays of distinct strings. This complete submission also supplies `implementation_id` and `source` locating real implementation checks. Describe preparation, the actual stimulus domain, prediction, sampling, comparison, mismatch reporting, and when checking occurs. Reasonable grouping and splitting are allowed; naming or item counts do not establish correctness.

Use UVM 1.2 with top `dvbench_top` and test `dvbench_test`. Connect the independent model to the scoreboard so that expected predictions are compared with actual DUT observations. Finish stimulus and checking, drain pending transactions, release objections, and output `DVBench_COMPLETED` once in the report phase only with zero ERROR/FATAL reports. Report mismatches with UVM_ERROR/UVM_FATAL. A completion marker does not replace actual checking.

Interact with the DUT through its native ports and preserve every port name, direction, width, and packed/unpacked index direction in `public/ports.md`. clock is the rising-edge clock; reset is synchronous active high. There are no inouts. io_rtcTick is a clock-sampled native input, not a second clock. Preserve all descending native ranges, including [25:0] addresses, [63:0] data, [7:0] masks, [9:0] source, [2:0] opcode/param, and [1:0] size. Instantiate the native DUT directly once in dvbench_top. Internal hierarchical access, force/release/bind, DPI, file/system probing, and DUT implementation copies are prohibited by the public restrictions. `sources.f` must list owned relative `.sv`/`.v` compilation units, one per line in dependency order, including `model/model.sv` and all UVM HDL. Do not put compiler options, absolute paths, parent traversal, or wildcards in the filelist. Submit `.vh`/`.svh` headers as owned include files; use literal relative includes within the submission, with `uvm_macros.svh` as the external exception. The model must not use includes.

## Mandatory Independent Model Entry Point

`model/model.sv` must define a self-contained SystemVerilog module named `dvbench_model`, matching the DUT's native port names, directions, widths, index directions, and public parameter profile. Use this identical file both for independent model evaluation and for prediction connected to the UVM scoreboard. Generate expected values only from reset, inputs, and their history; never read DUT actual outputs to construct expectations, instantiate the DUT in the model, or copy its implementation. A class, package, or function alone does not satisfy the required module entry point.

You have at most **300 cumulative agent decision turns**, with a delivery reminder at turn **250**. The budget persists across compaction and recovery of the same run. There is no whole-task wall-time or cumulative token limit. Compilation, simulation, and individual model requests have separate limits; read `public/deployment_budget.json`.

Read failed feedback and its listed compiler logs, simulation logs, and public-interface waveforms. Repair the submission and rerun while budget remains. A golden PASS is a debugging milestone: complete every required document, the independent model, and the UVM environment, and address known failures before finishing. Save the complete submission and report its actual verification status. Do not use subagents.

Use the framework's native file-editing tools. In Codex and OpenCode, `apply_patch` is a tool call, not a shell command; Claude Code uses `Write` and `Edit`. Use the framework's shell tool for commands. If required tools are unavailable, report an execution-environment failure instead of pretending that a tool call succeeded.
