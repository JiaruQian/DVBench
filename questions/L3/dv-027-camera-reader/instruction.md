# dv-027-camera-reader: Build a Complete UVM Verification Environment

Read `public/spec.md`, `public/ports.md`, `public/submission_format.md`, and `submission_contract.json`, together with `public/debug_feedback.md`. The native DUT top is `sf_camera_reader`. Use the fixed BUFFER_SIZE=12 profile. Preserve the independent rising-edge i_pix_clk capture domain and clk FIFO/read domain, and their separate synchronous reset behavior: !i_camera_reset or !i_clk_locked resets pixel capture/counting at a pixel edge, while rst or !i_clk_locked resets FIFO/cross-domain state. Camera reset is not asynchronous. The RTL implementation is hidden.

Submit `flow/features.md`, `flow/features.json`, `flow/testplan.md`, `flow/testplan.json`, a self-contained `model/model.sv`, complete UVM sources, and `sources.f` at the submission root. Features describe what to verify; the testplan explains legal preparation and stimulus, independent expectations, valid sampling, and failure detection. Each JSON document must carry all facts in full, and its Markdown partner must express the same IDs, references, facts, and methods. Markdown cannot fill omissions in JSON; follow the types, references, and paired format examples in `public/submission_format.md`.

`flow/features.json` uses a nonempty `features` array with `feature_id`, `requirement_ids`, `module`, `definition`, `interface`, `timing`, and `boundary`; an optional `parent_id` must reference an existing feature without cycles. `flow/testplan.json` uses a nonempty `tests` array with `test_id`, `feature_ids`, `requirement_ids`, `stimulus`, `expected`, `checker`, `implementation_id`, and `source`. Use nonempty strings for text and locator fields, and nonempty arrays of distinct strings for requirement, feature, and interface references. Use unique IDs, public requirement references, relevant native ports, and references to your own features and actual checking code. Reasonable splitting and merging are allowed. Describe preparation, drive timing, the actual stimulus domain, expected relationships and windows, and independent comparisons that can report a failure; naming or file existence alone does not establish checking.

Use UVM 1.2, top `dvbench_top`, and test `dvbench_test`. Provide the sequence, driver, monitor, agent/environment, predictor, scoreboard, checker, and coverage required by the public submission format. Connect the independent model to the scoreboard and compare separately observed actual and predicted values. Keep coverage separate from correctness checks. Report errors through `UVM_ERROR`/`UVM_FATAL`. After stimulus and checking finish, in-flight transactions drain, objections are released, and ERROR/FATAL counts are zero, output `DVBench_COMPLETED` once in the report phase.

Interact only through native DUT ports and preserve their names, directions, widths, packed/unpacked indices, clocks, resets, inouts, and contracted parameter profile. Keep i_pix_data[7:0], o_rfifo_size[23:0], and the [31:0] data/count/debug outputs exactly as published; preserve four-state semantics of the public debug port. List one relative `.sv`/`.v` path per line in `sources.f`, in dependency order, including `model/model.sv` and all required UVM HDL. Do not list compilation options, absolute paths, parent paths, wildcards, or a DUT implementation/stub. Except for tool-provided `uvm_macros.svh`, includes must use safe relative paths within the submission. Follow the public restrictions on internal hierarchical access, force/release/bind, DPI/VPI, and file/system/network probing; obtain permitted diagnostics through the feedback client.

## Mandatory Independent Model Entry Point

`model/model.sv` must define a self-contained SystemVerilog module `dvbench_model` with the native port names, directions, widths, index directions, and parameter profile in `public/ports.md` and `submission_contract.json`. It must not depend on UVM, includes, or other submission sources. Classes, packages, or functions alone do not satisfy the module entry point. Use this identical file for independent model evaluation and for predictions actually compared against DUT observations in the TB scoreboard. Generate predictions only from reset, inputs and their history. Do not instantiate the DUT, copy its implementation, or derive expected values from DUT actual outputs. Maintain the separately specified histories and reset effects of the pixel and read domains.

Keep feedback outside the submission directory. The service uses the golden design and seed 1; mutation results are available only after the submission is frozen.

## Execution budget and completion

You have at most **300 cumulative agent decision turns**, with a delivery reminder at turn **250**. The budget persists across compaction and recovery of the same run. There is no whole-task wall-time or cumulative token limit. Compilation, simulation, and individual model requests have separate limits; read `public/deployment_budget.json`.

Read failed feedback and its listed compiler logs, simulation logs, and public-interface waveforms. Repair the submission and rerun while budget remains. A golden PASS is a debugging milestone: complete every required document, the independent model, and the UVM environment, and address known failures before finishing. Save the complete submission and report its actual verification status. Do not use subagents.

Use the framework's native file-editing tools. In Codex and OpenCode, `apply_patch` is a tool call, not a shell command; Claude Code uses `Write` and `Edit`. Use the framework's shell tool for commands. If required tools are unavailable, report an execution-environment failure instead of pretending that a tool call succeeded.
