# dv-018-fifo-width-convert: Build a Complete UVM Verification Environment

Read `public/spec.md`, `public/ports.md`, `public/submission_format.md`, and `submission_contract.json`. The native DUT top is `width_convert`. Support all three fixed profiles: p4to8 (ISIZE=4, OSIZE=8), p8to4 (ISIZE=8, OSIZE=4), and p8to8 (ISIZE=8, OSIZE=8), using one parameterized model. The clock input is clock; rst_n is asynchronous active-low in the converting profiles, while the equal-width profile is combinational and ignores clock/reset. The RTL implementation is hidden.

Submit `flow/features.md`, `flow/features.json`, `flow/testplan.md`, `flow/testplan.json`, a self-contained `model/model.sv`, complete per-profile UVM sources, and the profile filelists described below. Provide complete UVM HDL and `profiles/p4to8/sources.f`, `profiles/p8to4/sources.f`, `profiles/p8to8/sources.f`. Filelist paths are relative to the corresponding profile working root; the assembler materializes the same root `model/model.sv` there, so the submitted model need not be copied three times. Features describe what to verify; the testplan explains legal preparation and stimulus, independent expectations, valid sampling, and failure detection. Each JSON document must carry all facts in full, and its Markdown partner must express the same IDs, references, facts, and methods. Markdown cannot fill omissions in JSON; follow the types, references, and paired format examples in `public/submission_format.md`.

`flow/features.json` uses a nonempty `features` array with `feature_id`, `requirement_ids`, `module`, `definition`, `interface`, `timing`, and `boundary`; an optional `parent_id` must reference an existing feature without cycles. `flow/testplan.json` uses a nonempty `tests` array with `test_id`, `feature_ids`, `requirement_ids`, `stimulus`, `expected`, `checker`, `implementation_id`, and `source`. Use nonempty strings for text and locator fields, and nonempty arrays of distinct strings for requirement, feature, and interface references. Use unique IDs, public requirement references, relevant native ports, and references to your own features and actual checking code. Reasonable splitting and merging are allowed. Describe preparation, drive timing, the actual stimulus domain, expected relationships and windows, and independent comparisons that can report a failure; naming or file existence alone does not establish checking.

Use UVM 1.2, top `dvbench_top`, and test `dvbench_test`. Provide the sequence, driver, monitor, agent/environment, predictor, scoreboard, checker, and coverage required by the public submission format. Connect the independent model to the scoreboard and compare separately observed actual and predicted values. Keep coverage separate from correctness checks. Report errors through `UVM_ERROR`/`UVM_FATAL`. After stimulus and checking finish, in-flight transactions drain, and ERROR/FATAL counts are zero, output `DVBench_COMPLETED` once.

Interact only through native DUT ports and preserve their names, directions, widths, packed/unpacked indices, clocks, resets, inouts, and contracted parameter profile. Preserve wr_data[ISIZE-1:0] and rd_data[OSIZE-1:0]; the 4/8 port illustration does not limit the other required profiles. List one relative `.sv`/`.v` path per line in each profile `sources.f`, relative to its profile working root and in dependency order, including `model/model.sv` and all required UVM HDL. Do not list compilation options, absolute paths, parent paths, wildcards, or a DUT implementation. Keep the model file self-contained. Follow the public restrictions on internal hierarchical access, force/release, DPI, and file/system probing; obtain permitted diagnostics through the feedback client.

## Mandatory Independent Model Entry Point

`model/model.sv` must define a self-contained SystemVerilog module `dvbench_model` with the native port names, directions, widths, index directions, and parameter profile in `public/ports.md` and `submission_contract.json`. It must not depend on UVM, includes, or other submission sources. Classes, packages, or functions alone do not satisfy the module entry point. Use this identical file for independent model evaluation and for predictions actually compared against DUT observations in the TB scoreboard. Generate predictions only from reset, inputs and their history. Do not instantiate the DUT, copy its implementation, or derive expected values from DUT actual outputs. The same parameterized model must support all three profiles, and each profile top must instantiate DUT and model with its corresponding fixed parameters.
