# dv-067-tagetable: Build a Complete UVM Verification Environment

Read `public/spec.md`, `public/ports.md`, `public/submission_format.md`, and `submission_contract.json`, together with `public/debug_feedback.md`. The DUT top is `TageTable`. There are no parameters or required defines. Retain the complete native 43-port interface in `public/ports.md`. The RTL implementation is hidden.

Submit `flow/features.md`, `flow/features.json`, `flow/testplan.md`, `flow/testplan.json`, a self-contained `model/model.sv`, complete UVM sources, and `sources.f` at the submission root. Features explain what to verify; the test plan explains how to establish legal conditions, apply stimulus, independently predict results, sample valid outputs, and detect failures. Each JSON file must carry the complete facts, and its Markdown partner must describe the same IDs, references, and semantics; Markdown cannot fill gaps in JSON. Use the field types, reference rules, and unrelated paired examples in `public/submission_format.md`.

The feature JSON root contains `features`; entries describe `feature_id`, `requirement_ids`, `module`, `definition`, `interface`, `timing`, and `boundary`. The plan JSON root contains `tests`; entries describe `test_id`, `feature_ids`, `requirement_ids`, `stimulus`, `expected`, `checker`, `implementation_id`, and `source`, as required by the format. Use unique IDs and valid references to public requirements, your features, and real implementation locations. Preserve all conditions, timing, and boundaries in both representations. Both roots are objects containing nonempty arrays. Required ID/text fields are nonempty strings; requirement, feature-reference, and interface arrays contain distinct nonempty strings. List the native ports relevant to each feature. Describe actual preparation and stimulus domains, concrete expected relationships, valid sampling, an independent comparison, and mismatch reporting in the plan. Reasonable naming, splitting, merging, and many-to-many references are allowed. Optional `parent_id` references an existing feature or is null, and parent relationships must not form cycles.

Use UVM 1.2 with top `dvbench_top` and test `dvbench_test`. Implement the sequences, driver, monitor, agent/environment, predictor, scoreboard, checks, and coverage required by the public format. Connect the independent model to actual/expected scoreboard comparisons; protocol checks or coverage alone do not replace prediction. Report mismatches with `UVM_ERROR` or `UVM_FATAL`. After stimulus and checking finish, in-flight transactions drain, objections are released, and ERROR/FATAL counts are zero, emit `DVBench_COMPLETED` once in the report phase.

Interact with the DUT only through its native ports. Preserve every port name, direction, width, packed/unpacked dimension, and index direction in `public/ports.md`. Use the sole rising-edge `clock` and synchronous active-high `reset`. All packed indices descend to zero; retain 64-bit histories, 40-bit PCs, 3-bit counters, and 2-bit usefulness fields with their published indices. There are no inout ports. List one submission-relative `.sv` or `.v` path per line of `sources.f`, in compilation dependency order, including `model/model.sv` and all required UVM sources. Do not put compiler options, absolute paths, `..`, wildcards, or a DUT copy/stub in the filelist. Includes other than tool-provided `uvm_macros.svh` must resolve within the submission, using safe relative paths. Do not use hidden hierarchy, force/release/bind, DPI/VPI, file/system/network probes, or parameter overrides outside the public contract. Instantiate the native DUT directly exactly once in `dvbench_top`. Submit at most 256 ordinary files and 16 MiB total. Do not choose compiler/simulator options, seeds, or a design variant, and do not use arbitrary dumps, escaped identifiers, or macro token concatenation. Standard UVM macros and ordinary empty header guards are permitted by `public/debug_feedback.md`.

## Mandatory Independent Model Entry Point

`model/model.sv` must define the self-contained SystemVerilog module `dvbench_model` with the native port names, directions, widths, packed/unpacked indices, and public parameter profile of this task. It must compile independently without UVM, includes, or other submission files. Use this identical file for independent model evaluation and for predictions consumed by the complete UVM scoreboard. Generate expected outputs only from reset, inputs and their history, never from DUT actual outputs. Do not instantiate the DUT or copy its implementation. A class, package, function, protocol checker, or actual-output loopback alone does not satisfy the module contract. Keep predicted and observed values separate and compare them in the valid windows specified by the public specification.

## Execution budget and completion

You have at most **300 cumulative agent decision turns**, with a delivery reminder at turn **250**. The budget persists across compaction and recovery of the same run. There is no whole-task wall-time or cumulative token limit. Compilation, simulation, and individual model requests have separate limits; read `public/deployment_budget.json`.

Read failed feedback and its listed compiler logs, simulation logs, and public-interface waveforms. Repair the submission and rerun while budget remains. A golden PASS is a debugging milestone: complete every required document, the independent model, and the UVM environment, and address known failures before finishing. Save the complete submission and report its actual verification status. Do not use subagents.

Use the framework's native file-editing tools. In Codex and OpenCode, `apply_patch` is a tool call, not a shell command; Claude Code uses `Write` and `Edit`. Use the framework's shell tool for commands. If required tools are unavailable, report an execution-environment failure instead of pretending that a tool call succeeded.
