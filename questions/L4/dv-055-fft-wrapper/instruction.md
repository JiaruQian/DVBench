# dv-055-fft-wrapper: Build a Complete UVM Verification Environment

Read `public/spec.md`, `public/ports.md`, `public/submission_format.md`, and `submission_contract.json`, together with `public/debug_feedback.md`. The DUT top is `fft_wrapper`. Use only `DIVISOR=5`, `N=16`, `Q=8`, `ADDR_WIDTH=5`, `DATA_WIDTH=16`, and `DEPTH=32`. RTL is hidden.

Submit `flow/features.md`, `flow/features.json`, `flow/testplan.md`, `flow/testplan.json`, self-contained `model/model.sv`, complete UVM sources, and `sources.f` under the submission root. Features describe what to verify; the test plan explains legal preparation, stimulus, independent expectations, valid sampling, and failure detection. JSON must carry the complete facts, and each Markdown/JSON pair must agree semantically under the same IDs and references; Markdown cannot fill JSON omissions. Follow the public format for field types, unique IDs, native-port references, public requirement IDs, and links from tests to your features and actual implementation. The feature JSON root contains a nonempty `features` array; entries provide `feature_id`, `requirement_ids`, `module`, `definition`, `interface`, `timing`, and `boundary`. The plan JSON root contains a nonempty `tests` array; entries provide `test_id`, `feature_ids`, `requirement_ids`, `stimulus`, `expected`, `checker`, `implementation_id`, and `source`. Use the public format for nonempty strings, distinct reference arrays, optional parent relationships, and real HDL implementation locators. Explain conditions, timing, and boundaries in the feature fields and concrete stimulus, expected behavior, and checker methods in the plan fields.

Use UVM 1.2 with top `dvbench_top` and test `dvbench_test`. Provide working stimulus, driving, monitoring, prediction, scoreboard comparison, checking, and coverage as required by the public submission format. Connect the independent model to the scoreboard and compare separately wired actual and expected outputs. After stimulus and checks finish, drain in-flight work, release objections, and confirm zero ERROR/FATAL before printing `DVBench_COMPLETED` once in the report phase. Report verification failures through UVM_ERROR/UVM_FATAL; the completion marker and coverage do not replace checking.

Interact with the DUT through its native ports and preserve the public port names, directions, widths, packed/unpacked dimensions, and index directions. Use rising-edge `clk` and asynchronous active-high `rst`. Preserve `m_addr[4:0]`, `s_addr[4:0]`, `m_data[15:0]`, and `s_data[31:0]`, with the public real/imaginary packing. There are no inout ports and no native start/ready/done handshake. List one submission-relative `.sv`/`.v` path per line in `sources.f`, in dependency order, including `model/model.sv` and all UVM compilation units. Do not list compilation options, absolute paths, parent paths, wildcards, or a DUT implementation/stub. Resolve includes within the submission, except for the tool-provided `uvm_macros.svh`. Do not use internal DUT hierarchy, force/release/bind, DPI/VPI, file/system/network probing, or parameter overrides outside the public profile.

## Mandatory Independent Model Entry Point

`model/model.sv` must define the self-contained native-port SystemVerilog module `dvbench_model`, matching the public interface and supported parameter profile, including port directions, widths, and index directions. It must compile independently of UVM and the other submission sources. Use this identical file for independent model evaluation and actual prediction in the UVM scoreboard; a class, package, or function alone does not satisfy the module entry point. Derive expected outputs only from reset, stimulus inputs, and their history; do not instantiate the DUT, copy its implementation, read DUT actual outputs as predictions, or replay golden output. Drive model predictions and DUT actual outputs on separate nets.

## Debugging

Read `public/debug_feedback.md`. Submit a snapshot with `bash /public/environment/run.sh simulate --submission /submission --output /tmp/feedback-01.json`. Keep feedback outside the submission directory. The service uses the golden design and seed 1; mutation results are available only after the submission is frozen.

## Execution budget and completion

You have at most **300 cumulative agent decision turns**, with a delivery reminder at turn **250**. The budget persists across compaction and recovery of the same run. There is no whole-task wall-time or cumulative token limit. Compilation, simulation, and individual model requests have separate limits; read `public/deployment_budget.json`.

Read failed feedback and its listed compiler logs, simulation logs, and public-interface waveforms. Repair the submission and rerun while budget remains. A golden PASS is a debugging milestone: complete every required document, the independent model, and the UVM environment, and address known failures before finishing. Save the complete submission and report its actual verification status. Do not use subagents.

Use the framework's native file-editing tools. In Codex and OpenCode, `apply_patch` is a tool call, not a shell command; Claude Code uses `Write` and `Edit`. Use the framework's shell tool for commands. If required tools are unavailable, report an execution-environment failure instead of pretending that a tool call succeeded.
